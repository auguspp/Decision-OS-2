# 沪深 A 股日数据：持续保管、增量更新与正常读取

责任：#10，来源和保管分别复用 #12 与 #6 的原合同。这个入口把一次检查变成可接续的数据链：保存已经成功取得的页，按交易日保留全市场分区，正常读取明确版本，在下次显式更新时只补必要查询。实际生产启用与真实供应商可用性仍以原任务中的运行和保管回执为准。本仓现已整体 private，仍使用同一 records 分支；受信入口每次核原生可见性，不改原 repository_id、store_id、anchor 或历史公开建仓标记。已有来源访问及保管授权按原 A 股任务范围接续；对外公开原始供应商数据仍须逐来源单独核定再分发权。

## 数据范围与“可用”的含义

当前集合覆盖 SSE/SZSE 的 `stock_basic(list_status=L)` 已识别证券。它是当前上市状态快照，不是历史时点证券全集；BSE、退市/暂停上市状态、逐日历史成分不能被称为已覆盖。名称、身份冲突、上市日期、交易所日历、行情、因子和停复牌各自通过原资格检查。主表缺失时完整分母未知，不能将其当成零。

每个开市日保存原 `daily`、`adj_factor`、`suspend_d` 查询。数据按 `trade_date` 对全市场请求，读取时才选择证券和展示页；不会为每只证券另发同一批历史来源请求。两所原日历分别确定实际截止交易日，周末和节假日不会按最后收到的价格回退。日终入口最多取上海时间的前一个自然日，不宣称盘中实时行情。

顶层 `raw` / `qfq` 沿现有完整逐日窗口算法计算 5/20/60 个交易日结果；原字段、资格和计数含义保留。前复权沿原截止日因子比值，不能当总回报或公司行动完整认证。因子错误只限制相关 qfq，原价与其他证券仍按实际资格展示；停复牌证据只解释缺口，不补价格、不自动证明全天停牌。新上市、停牌、资料缺失可能导致窗口不可用，即使全部声明查询已经完整保存。

持续集合的正常读取另返回 `endpoint_comparisons`（`relay-ashare-endpoint-comparisons-v1`），落实[最终设计 §7.3](../decision-os-2.0-design.md)按用途判断所需观测的规则。它不更改原保管 schema 或另建输入源。

| 用途 | 所需观测 | 缺口的影响 |
|---|---|---|
| 原 `raw` / `qfq` 完整逐日窗口 | 日历中基准至截止的 N+1 个实际市场时点，及原复权依赖 | 窗内任一天缺失仍限制原窗口；不由端点结果补齐 |
| `endpoint_comparisons.raw` | 同一交易所日历中的第 N 个交易日前基准与原实际截止日的合格价格 | 只缺中间价格不阻断两端比较；缺任一端点不得改用邻日 |
| `endpoint_comparisons.qfq` | 上述两端价格、两端因子，沿原截止日因子归一化 | 各窗单独调用原 `_adjust` 口径；中间坏因子或其他窗口基准异常不牵连本窗，所需因子未知不填 1 |

每个端点结果明确 `comparison_basis=calendar-endpoints-v1`、交易日间隔、原基准/截止日期、两端值、状态和价格比率。日历不足时不按收到的价格行数凑窗；日期、价格、重复行及范围沿原校验。端点输入按原查询区分缺失、隔离、未恢复和上市范围外，来源定位沿集合原整市场日查询的 `source_lineage` 及正常 reader 的 exact 引用，不伪造按证券的 SourceRef。即使端点价格比率是零，也保留为真实可用结果。

端点 `raw` / `qfq` 分别返回完整声明分母、至少一个窗口可用的 `observed_count`、无窗口可用的 `missing_count`、未全部可用的 `incomplete_count` 和逐窗计数。主表隔离项仍在分母；未声明证券不计入可用分子，缺主表时完整分母与缺失计数仍为 `null`。分页和精确证券查询只截取展示行，不改变全域计数；`view_version` 包含端点用途、摘要和所有证券的完整端点结果，并与分页无关。原 `raw` / `qfq.source_version` 继续表示其原输入身份，不把新用途冒称新的来源取得。

端点可用只说明该用途的观测成立，不提升集合 `complete`、原严格窗口、正常读取服务状态或 freshness，不证明完整逐日路径、波动、事件反应或总回报。正常 CLI 和[阅读室](../delivery/reading-market.md)传递同一结果，健康回执仅增加独立端点安全计数，不输出证券、价格、因子、来源正文或 SourceRef。运行队列、有限单元、请求额度、原 220 槽连续计划及各页终态继续按原合同执行；本用途不启动来源访问。

集合完整、来源可恢复、窗口可用、当前时效是四个独立事实。读取上一完整集合时，页面保留其原价格和 SourceRef，同时显示最新尝试的失败或暂停。当前新日历可以证明旧集合实际落后几个交易日；没有覆盖读取时点的日历证明时，freshness 为 unknown，不会因旧截止日内部没有缺口就显示当前健康。

日历成功或一页主表保管成功只能证明该部分已取得；完整主表分母和真实行情窗口仍须各自成立。日期单元从最新交易日向前填充，已有用途可先独立读取：例如完整 5 交易日窗口需要包含基线的 6 个实际市场时点，而明确标注的 5 交易日端点比较只需其中两端；20/60 的未取历史保持原用途相应缺口，不将短窗通过写成全部完成。新股、停牌或坏因子可以限制个别证券的窗口，但必须保留完整声明分母、可用与缺失计数。原代尚未满足接续条件时，短窗或端点可读也不授权换代跳过待填历史或失败预算。

## 唯一数据链与接续

没有新数据库或另一份可写 current。原 `source-views` 与 `submissions` 保管以下版本：

| 对象 | 保存内容 | 成立的事实 |
|---|---|---|
| 来源页 | 原 requested-column projection、身份、查询范围、原页元数据 | 原 SourceInput/SourceRef 可精确恢复，非原始 HTTP 字节 |
| 执行检查点 | 原请求、页偏移、每次尝试、等待、请求预留及成功页引用 | 同一失败页的尝试/等待预算可以跨进程延续 |
| 完整查询清单 | 经检验的原 use/query_key 与完整页引用 | 原查询已终止并可独立读回 |
| 集合根 | 固定计划、日期单元、查询/检查点引用、前驱及上一完整根 | 明确这个版本保管了哪些分区 |

每次 HTTP 前，先通过原 CAS writer 保存该页的尝试预留，并由新 reader 读回。成功页保存后再保存控制状态。完整检查点晋升为查询清单时，核验其原始页身份后直接引用，不重放已成功页的逐项写入。保存失败、返回未知、读回失败都先停止；原 journal 和 exact 引用是后续对账入口。

原单页最多 4 次尝试和 180 秒等待，来源工作单元仍按 600 秒窗口作准入。持续 collection 的默认客户端固定使用 90 秒 socket timeout，以提高全市场响应正文停顿时的有界耐受；其他 Relay 业务默认保持 30 秒。可信构造参数 `request_timeout_seconds` 仅接受 30..90 的整数，并以只读属性供重试器绑定实际值；它不进入查询参数、RetryPolicy 或检查点 schema。首次请求、失败后的下一次请求、跨单元的剩余等待及持久预留后的再次检查，都须为同一实际 timeout 留足窗口。业务重试仍至少等待 30 秒，长有效 Retry-After 优先。

Socket timeout 约束阻塞 socket 操作，不是完整 HTTP 请求的绝对墙钟 deadline，不能据此承诺请求总耗时不超过 90 秒或整个单元严格在 600 秒内结束。跨工作单元不刷新原页的次数及等待额度；等待的剩余时间按原 not-before 计算。若持久预留及读回后已不足实际请求窗口，以 `RELAY_CHECKPOINT_ADMISSION_EXPIRED` 停止，不发 HTTP，也不抹去原 in-flight 预留或假定请求未发出。旧检查点按原请求和剩余预算接续，成功页与终态不因 timeout 配置变化重开；已保存的完整检查点可在没有 Relay 凭证时完成查询恢复，源 HTTP 为零。

收到已核 URL 的 HTTP200 响应头后，若正文读取发生 timeout、断连或不完整读取，检查点保留实际 HTTP 状态、安全响应头和原传输失败分类，仍不是成功页。已经收到的 Retry-After 继续约束原重试器；长等待不截短为30秒，无效或被屏蔽的等待值按原规则停止。连接或等待响应头阶段的失败没有已观察状态，仍记为未知；旧记录缺少的响应头不能事后推断补写。这些事实沿既有检查点字段保存，不增加原页尝试或等待预算。

一个 `collection_id` 跨所有 generation 只有一条唯一后继链。运行入口从实际绑定中核真实末端，旧根、旧检查点、隐藏新检查点或分叉都不能授权重复请求。原 generation 还有 pending/paused/blocked/unknown 状态时先在原代接续或对账；不能换代跳过限流或恢复原页已耗尽的额度。新代刷新已经完整的 current-L 主表，原终止失败主表保留其失败；原日期查询复用 exact 版本。仅 `refresh_dates` 明确列出的已完整日期可以重新取得；它不重置失败查询。

新代的 `end` 与 `calendar_end` 不得倒退，已经使用的旧 generation 不能重开。历史版本仍可按原 SourceRef 读取。运行没有可推进单元时明确返回 `ASHARE_NO_PROGRESS`，不会持续空转重建预算。

## 四个原终态的一次显式有限维修

普通 `sync` 仍跳过已经耗尽的原终态。一次性 `repair` 只适用于原 `cn-eod / g20261016` 中 `20261015`、`20261016` 的 `daily` 与 `adj_factor` 四个指定槽：同一原计划、Registry、use/query_key、参数、两页上限，以及各槽原零成功页、四次 timeout 的完整终态引用必须逐项核回。权限、限流、未知 in-flight 或未知写入不属于可借此重试的失败。旧检查点的 terminal 重启拒绝继续生效；原四个 unit、失败诊断、原次数及等待不会被覆盖。

**维修增加总体来源请求预算。** 原四条查询已经发生的 16 次请求保留；唯一新 episode 每槽最多两页、每页四次尝试和 180 秒等待，合计最多 **32 次新增 HTTP**，原加新最多 48 次。未用额度不能跨槽转移，不追加第三页，不创建第二 episode。成功页不重取，暂停只接续同一新检查点的剩余次数、等待和偏移。用保管链中的每页 attempts 及未解决的请求预留推导已用额度，并对同页的 capture/control 表示去重；运行回执计数不能替代这项预算事实。

首次 `repair` 将集合保管根由 `market-collection-custody-v1` 升为 `market-collection-custody-v2`，在同一次根写入中保存不可变 grant。grant 绑定 then-current 唯一根、原四个 exact terminal refs、原固定请求和成功传输证据；新 capture ID 只用于定位，不自行授予额度。激活独占一个源 HTTP 为零的有限单元，完成原生核验、保存和独立读回后，后续单元才可消耗追加额度。首次写入、以后继承、独立恢复和唯一后继链共同验证 grant，不得删除、替换或降回 v1。换 generation、改变 refresh 或重新命名不能把已使用事实清零。仍使用同一 records、原 CAS 和独立 fresh 读回；保管未知、旧根、分叉或隐藏的新检查点均先对账，不发新的来源 HTTP。

启用证据须包含同原计划中一份完整 `daily` 和一份完整 `adj_factor` 的 exact query、complete checkpoint 及首次完成 collection 根，并由新 reader 恢复原请求、成功页和关联。原生 Actions 元数据另外核同仓 `main / workflow_dispatch`、原 workflow、run/attempt 和代码 SHA；一个因整集合未完成而正常返回 partial 的 run 不会抹去其中完整查询的事实。证据代码 SHA、grant 首次启用代码及每次维修 attempt 的实际执行代码分别保管，并核原生承接关系；执行 SHA 来自受信宿主，不接受输入 JSON 自称“已验证”或自填执行身份。首次发布 grant 和发源请求前，维修代码仍须正常 PR、完整 CI、实际 main 验收，并取得上述真实成功原件的独立恢复证据。

原失败状态与有效查询分别保留。只有完整且通过原 query/页面资格与独立恢复的维修结果可以进入原槽的有效查询选择；summary、集合完整性、换代继承、正常 reader 和运行进展使用同一语义。计数同时呈现原失败和维修后的有效状态，不把只改时间戳视作进展。正常读取继续使用 `current-complete` / `current-partial` 等原服务状态，并附维修来源；raw/qfq 算法、完整分母、停复牌解释、5/20/60 窗口及时效标准保持。

`repair` 必须显式手动调用。首次请求提供有界 `repair_request`，包括原根、四个 terminal refs 和两类传输证据；其中没有可任意提高额度的 budget 字段。后续继续同一 grant 时留空该请求，不发布另一份 grant。普通 `sync` 只推进原 pending/paused 单元并继承已核维修结果；`status` 与读取不取得来源凭据，也不启动维修。原 600 秒准入窗口、240 次 Store API 来源准入、512 次单元硬上限、原生 quota、同串行组及 private/公开权利门禁全部适用。维修再次终止时保留实际剩余缺口，不继续申请第二 episode。

## 日常操作：沿用现有 records

**唯一保管目标是本仓已经存在的 `records` 分支**，随同仓整体 private 继续使用。`config/store-binding.json` 是可信只读配置，保留现有仓库 ID、分支、anchor、store_id、建仓时的公开标记和单向私有化选项；实时可见性另外由 GitHub 原生 API 核查，不从配置或来源文本推定。绝不把 `write_enabled` 永久修改为 true。运行时的写入能力仅由受信的、显式授权 `sync` 或原 private 目标的有限 `repair` 分支临时授予。无需创建 `Decision-OS-2-data`，也不需要第二种保管平台或新的市场仓。

先编写有界选择文件，例如：

```json
{
  "collection_id": "cn-eod",
  "generation": "g20261016",
  "start": "20260701",
  "end": "20261016",
  "calendar_end": "20261016",
  "refresh_dates": []
}
```

`start` 至 `calendar_end` 最多 119 个自然日；真实交易日由两所日历派生。新增日期在后继 generation 补齐，不自动重抓已成功的旧日期。`plan` 不需要登录：

```bash
python -m decision_kernel.interfaces.market_collection_cli plan \
  --selection /runtime/selection.json --out /runtime/plan.json

# 正常独立读取使用现役 records 绑定，仍须具备该仓只读 GitHub 凭据。
python -m decision_kernel.interfaces.market_collection_cli read \
  --binding config/store-binding.json --selection /runtime/selection.json \
  --out /runtime/reading.json
```

GitHub Actions 的 `decision-os-ashare-data` 仅手动 `main` 运行 `status`、`sync` 或上述有限 `repair`，填写精确 `code_sha` 与 selection；`status` 只读，**不需要来源密钥或公开授权声明**。如果尚无市场集合，返回 `ASHARE_COLLECTION_NOT_RETAINED`，并不表示空数据已经通过验收。`repair` 限原生核验 private 的原保管目标；首次 `repair_request` JSON 最多 16,000 UTF-8 字节，续取同 grant 时留空。`sync` / `status` 不接受非空维修请求。这个手动托管入口负责原生运行/代码关系核验，本地 plan/read 不成为跳过该核验的维修入口。

`sync` 每次 1..32 个明确有限单元。操作人必须确认 **原来源访问及保管范围** `access_and_custody_confirmed`；当 GitHub API 验证仓库为 **public** 时，还必须确认 **所选全部来源行可公开再分发的独立法律/许可依据** `public_rights_confirmed`。当前原生核验 private 时，已获准的原任务可运行 sync，无需虚填公开权利，但仍须遵守原来源使用及保管许可。公开权利确认只表示已有的独立依据；选择 `records`、购买接口访问权、知道密钥或资料来自公开信息，都不能单独证明公开再分发权。授权未满足时，workflow 执行**无源凭据的拒绝作业并明确失败**，不进入 sync job；工作流的 GitHub 事件私有标记仅用于保守路由，入口自身重新通过 GitHub API 核真实可见性，在任何来源 HTTP 和 Store 写入之前拒绝假私有。不能为取得绿灯而绕过该检查。

通过许可核查后，直接再次显式调度 `sync`，原断点、分页、失败预算和原始 SourceRef 保持。不会循环定时或后台重试，也不会因跳到新 generation 恢复耗尽预算。

## 手动托管运行与资料权利

`.github/workflows/ashare-data.yml` 分别运行：`status` 获得 `contents:read`、无 Relay 密钥；`sync` 仅在来源范围授权且（公开再分发授权成立，或事件中仓库为私有）时进入，获得 `contents:write` 和既有 `TUSHARE_PROXY_API_KEY`；有限 `repair` 另外要求原目标 private，并以 `actions:read` 核原传输 run。入口在源调用前再次用 GitHub 原生 API 核当前可见性。三个入口沿同一串行组和受信 `config/store-binding.json` 确认原历史公开建仓的 `records`；GitHub 作业令牌直接传给原 `GitHubStore`，**无需新增数据仓、私有绑定 Secret 或专用市场 Store Token**。注意 `contents:write` 在 GitHub 平台层面是仓库权限而不是分支级隔离；唯一分支目标由应用绑定/anchor、CAS 和单一 writer 约束，不宣传它具有更强的平台强制隔离。

Actions 的 `result.json` 仍仅可包含操作、计数、日期、状态、允许的原生额度字段与代码/run 身份，不能包含任意来源行、证券名称、价格、SourceRef、Token 或原供应商错误正文。宿主同时将这同一份安全回执输出到 stdout，使 artifact 无法取得时仍可沿原生 job 日志诊断；不是另造一份成功状态或输出源数据。这个回执不等于已把数据集合保管成功；仅原 `records` 上可独立读回的 exact 引用才证明保管。

**公开目的地仍单独需要再分发许可。** 当前同仓 private 的实际取材与保管沿已有授权接续；私有仓并不豁免 Tushare 的用途、商业或保管限制。原核查的[Tushare 数据服务协议](https://tushare.pro/document/1?doc_id=405)描述个人、不可转让、非商业许可，不能据此推定可以将原始行情大批量公开到 GitHub。若目标为 public 且无相应公开再分发依据，只允许 `status`，不允许真实 `sync`；已核验 private 的原范围合法 sync 不受这个公开前提阻塞。计数回执始终不能冒充恢复了供应商源行。

旧 `market-custody`、研究写入和其他工作流继续使用它们原有的绑定与授权。原[阅读室](../delivery/reading-room.md)的只读宿主可以在原生核验 private 后读取获准集合，且须在释放输入引用、正文及页面前再次检查可见性；不扩大其他写入口，也不将私有材料迁入公开输出。首次合法回填的验收仍须分别记录原来源、exact 集合、跨进程只读恢复、真实分母和 raw/qfq 窗口/时效，不以工程 CI 代签。备份与离线恢复只证明原固定快照；它们不自动覆盖备份后新增的集合、页或后继研究。

## 容量、停止与恢复

每个显式工作单元共用一个原 GitHubAPI，writer 与所有新 reader 共同计入原 512 次请求。正常完整读采用只读 `GitMarketReader`：认证绑定并固定 Git 版本，读取原生 GitSnapshot，结束前再次核实际可见性和可达性。临时原生对象只供这次受控读取，不发布成公开恢复包。

API 达到 240 次的来源准入门槛时，先保存可续取停点，为后续检查点、查询清单和集合根读回留余量。不是把单次硬上限改成 240，也不是故障后清零 512。只有已经结束并保存的显式单元才允许下一单元建立预算；已知全局拒绝、未知写入、原页尝试耗尽或无进展不自动进入下一轮重试。

GitHub 原生额度与单元内的 512 次请求上限分别核算。一个显式 run 的所有单元共享原生响应中的合法 `limit`、`remaining`、`reset` 及资源观察，新建单元 API 不清空这些观察。取源前须为本单元原 512 上限尚余的请求预算保留原生额度；已知低额度或不足以证明可准入时，保留已确认的原停点，以 `paused / ASHARE_REMOTE_RATE_LIMIT` 结束本 run，不继续新单元、不自动等候重跑。已经发生的原生拒绝、持久化失败或未知写仍按原实际错误处置，不能改记为安全暂停成功。单元内 240 次准入门槛、512 次硬边界、原成功页和分页/失败预算不变；后续显式操作仍从原 exact 检查点核真实额度后接续。

总库存上限 8192 个来源/研究/制品版本，recursive tree 最多 32768 项，原生 Git 下载最多 64 MiB；旧扁平查询仍限 1024 个版本，有界搜索每次最多扫描 32 个。每次来源工作单元预留 160 个目录项、32 个版本、8 MiB 原生空间及 256 KiB 的 GitHub 树响应预算；不知道线上真实大小时拒绝准入。本地合成 GitStore 明确不适用 GitHub 响应估算，但仍核实际原生大小。原 HTTP/响应、输入、单页与提交字节边界继续分别约束，最先到达的边界生效。

GitHub writer 在发送任何提交前还检查新文件加入后的完整树：目录项、总版本和包含路径/URL/格式余量的响应字节估计均须在原边界内。这样不会先写入一个正常读取无法展开的新 head，再把超限当作成功后的未知结果。

集合链发现也有独立的 8192 节点 / 512 MiB 累计唯一清单正文字节边界，在新根写入前预留本单元两个最大根（各 1 MiB 集合及 64 KiB 固定元数据余量）。这个字节数衡量逻辑清单，不是内存常驻量或允许下载的原生 Git 大小。同范围重复父引用仅在完整 exact SourceRef 已验证时复用，仍核选择、原提交可达性、字节和 owner。容量回执是当前有限余量，不是无限历史、备份成功或长期在线率。逼近边界时停止新取源，保留现有 exact 版本可读；扩容、受控归档或迁移按现有单一 writer/精确引用合同处理，不隐式删除老数据，不创建第二写入真源。

已保存的成功页不会因运行结束而丢失；未知响应的原始网络结果仍可能无法重建，必须保留该事实。恢复到更早源码版本不会删除新数据；暂不理解新 schema 的旧 reader 也不能被称为恢复成功。退出本能力时一起处理专属 collection/runtime/工作流/测试及本文入口，保留原共享来源、版本保管、raw/qfq、研究与 CI 保护。

## 验证责任

新反例分别覆盖源执行检查点、保管和 native snapshot、5000 以上证券与多日窗口、跨进程续取、增量和旧完整版本、全代防回退、普通 CLI/room、有限运行宿主与容量边界。全部合成数据测试明确不代签供应商返回是否正确、资料权利或生产长期健康。完整精确 head CI、普通 merge 后实际 main、真实运行与独立消费者各自保留原生证据。

一次维修的保护由 collection owner 维护：旧 terminal 重启仍拒绝，重复 grant、降版、换代清账、错槽/引用/use、隐藏 tip、未知写与成功页重放均拒绝；同 grant 跨单元接续、预算推导和正常消费须实际验证。追加执行结束不删除其历史语义；以后退役该次执行入口时，同步移除专属手动 job 与启用核验，保留 v2 独立恢复、有效查询选择和原链约束，不能让已保管数据失去现役读取器。
