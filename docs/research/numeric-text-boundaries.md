# 数值文本边界：不能丢掉负号再核正数

本页细化[现役数值核对](numerical-audit.md)的“完整数字”约束，责任仍为 #7。
它不是新解析平台、数值 schema 或研究方法；`SourceRef` 和原正文不变。

原 ASCII 邻接检查会接受从 `−50`、`－50`、`- 50` 中选择出来的 `50`，
可能把亏损或现金流出当成正数。现役定位器现在检查选择内部的首尾空白、
相邻的兼容数字/标点、同一行内被空白或格式字符隔开的符号，并拒绝
括号可能表示会计负数的局部取值。典型失败为 `PARTIAL_NUMERIC_TOKEN`。

`NFKC` 仅用于观察边界字符，不改原始来源、Unicode 字符位置或选中字符串。
使用 Python 标准库 [unicodedata](https://docs.python.org/3.12/library/unicodedata.html)，
无需新增依赖。支持范围仍由原严格十进制字符串合同决定；完整 `−50`、
`(50)` 等未支持格式不会被偷偷转换成 `-50`，更不会被当成 `50`。

## 处置

- 完整 ASCII `-50`、科学计数和千分位仍按原合同处理。`50万元` 中的数字与
  明确单位仍可分别核对，不把中文单位当额外数位。来源换行是布局边界，不跨行猜符号。
- 横线可能是列表标记，括号也可能只是解释性标点。本检查选择拒绝这种歧义，
  **不是自动断定它们都是负数**。使用有资格且保留原口径的结构化来源，或保留
  未核问题并人工审阅；不得删除负号、改原文或把来源值改填成假设来换取通过。
- 一个数值被拒绝时，其后继计算不可用；无关的合格输入/计算继续输出。
  `conditional` 仍不是事实已独立核验或经济质量通过。
- 老研究的原文、哈希、回执与引用不改写。使用修复后代码重新核算时，原先错误
  通过的取值会被拒绝；这不追溯改写旧运行日志，也不把错误说成来源被篡改。
  真正修正研究时仍走正常新修订及确切前驱，不能覆盖历史。

专属反例覆盖 Unicode/全角负号、分隔空白/格式符、会计括号、局部数字和
选择内部空白；同组真实本地 Git 测试覆盖错误依赖隔离、新旧来源和旧附录重审。
这是工程回归，不证明已经完成某家公司 Full、取得原始 PDF 或获准公开个案。
退出文本来源数值定位时一并退出专属反例/说明；共享来源、算术及保留合同继续维护。
